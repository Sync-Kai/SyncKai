# Security and account-bound data

Sessions and epochs, encrypted tokens, episode guards, tracker writes, host patterns, CSP, images and messages. Part of the project memory (`CLAUDE.md` › Project memory).

- **Account-bound data**: the sync queue, « À noter » cards, recent syncs and corrections carry the `epochs` of the sessions open when they were created (`getOpenSessions`); nothing is written to a service whose session has changed (checked right before the write), and `clear*Session` purges the disconnected service's share. Manual end of session: `endSession(service)`; token rejected by the API: `endSessionIfToken(service, token)` (a reconnection in the meantime is preserved). Any account-bound write after a network request (profile, comparison, Agenda week, renewed MAL token) captures the generation BEFORE the request and goes through `writeIfSession` / `writeIfSessions` (or `saveRefreshedMalToken`) under the storage lock. List writes (L2, `chore/audit-leftovers`): `runGuarded` (`background/entry-commands.ts`) reads and writes through `tracker.forSession(epoch)`, whose requests read the token with `getValidToken(epoch)` / `getMalToken(epoch)` (`browser/tokens/access.ts`: token and `sessionEpoch` in ONE storage read, `readSessionToken`), so a sign-out then sign-in to another account between the last session check and the request throws `SessionChangedError` (`shared/session-epochs.ts`) before anything is sent, mapped to `sessionClosed()`; the AniList client reads a session-bound token again after its 429 penalty and budget wait (up to a minute), so a sign-out during the wait sends nothing (TRK-02). `decide(current, tracker)` receives that bound tracker: write through it, never through a tracker captured outside. The list alignment job (`compare.ts`) records the sessions open at its start (`CompareJob.epochs`; absent on a job of an earlier version = current sessions) and writes each item through `runGuarded`; a closed or replaced session stops it (`compare.error.notConnected`). A rejected token (`endSessionIfToken`) sets `sessionExpired:<service>` (« Session expirée » in the UI), cleared by a voluntary sign-out or a sign-in.
- **Encrypted OAuth tokens** (since 2.2.0): `anilistToken` / `malToken` are `{ v: 1, iv, data, expiresAt }` (AES-GCM, `src/browser/tokens/crypto.ts`), with a non-extractable key in the `synckai-vault` IndexedDB of the extension's origin (`browser/tokens/key-store.ts`, in memory in tests via `src/test/setup.ts`). Decryption in the service worker only (`browser/tokens/access.ts`: `getValidToken`, `getMalToken`, never under the storage lock); pages read presence without decrypting (`hasValidAniListToken`, `hasMalToken`, `getOpenSessions`). A legacy plaintext token is encrypted on first access and on update; an undecryptable token (lost key) closes the session with « Session expirée ». Compare decrypted tokens, never encrypted ones (fresh IV on every write). Sign-in (`saveToken` / `saveMalToken` → `saveSessionToken` in `browser/storage/tokens.ts`): sealed before the storage lock, then token write and `sessionExpired` removal under it; a token already stored (expired AniList token, or a MAL session open from two pages / a double click) first closes that session like a sign-out (`clearAniListSession` / `clearMalSession`: new epoch, account data purged), on both services (B8 / SEC-14). The « user » data (simple « À vérifier » cards, dismissed suggestions, airing state, learned links…) then goes only if the account now signed in is not the cached profile's, or cannot be read, and no other service is connected (`background/trackers/sign-in.ts` › `signIn` → `endPreviousAccountData`, STO-01, owner's decision 11 b of 2026-11-13): the same person reconnecting keeps it. Account ids are compared in memory only, never copied or logged. Threat model (SEC-07): the key lives in the same profile's IndexedDB; encryption defeats content-script and web-page reads of `storage.local` and accidental leaks (backups, diagnostic report, a devtools copy of the storage), NOT an attacker who can read the browser profile folder. `expiresAt` is in plaintext and outside the AES-GCM additional data (only `synckai:<service>-token:v1` is bound): tampering with it only changes what the pages show (`hasValidAniListToken`), the service worker trusts the decrypted copy (`getValidToken`); binding it would need a `v: 2` format and a migration (not done).
- **Episode guards** (`fix/episode-guards`, decision 1 = audit SEC-01 option b, 2026-10-16): the episode comes from the page, so a page script can forge it. (1) Rate limit of `EPISODE_COMPLETED` (`background/sync/episode-rate.ts`): more than `MAX_COMPLETIONS` (5) within `COMPLETION_WINDOW_MS` (10 min) for one tab (`tab:<id>`) or one series (`series:<exclusionKey>`) → `syncEpisode(…, { review })`: a « À vérifier » card with the sure entry proposed (`sync.review.burst`), nothing written; timestamps in `chrome.storage.session` under `EPISODE_RATE_KEY` (survive a worker restart, never `local`); storage error → not limited. An autoplay chain (one episode every few minutes, 2-min shorts included) stays under it. (2) `rules.ts` › `isFinaleJump`: live sync writing the last episode from more than `FINALE_JUMP_LIMIT` (12) episodes behind (absent from the list = 0) skips that service (`sync.review.finaleJump`) and creates the card; other services are written; a confirmed card, a correction and +1 / −1 are never guarded. (3) `rules-engine.ts` › `bridgeProofCapped`: on Crunchyroll and Prime Video (title-only platforms whose signals come from a MAIN bridge), a `high` result is kept only if the rules alone, without the signals, give the same entry and progress, or if they are undecided and the entry is linked or in the linked franchise; otherwise `low` with the entry proposed (Prime Berserk / Vinland Saga S2 and the adversarial corpus cases `adv-*`: a forged year can no longer move Frieren S1 to S2). Netflix / Disney+ were already covered by `gateByPlatformLink` (frozen by tests), ADN signals come from the page's JSON-LD (not capped). `isEpisodeInfo` bounds its strings and requires finite, non-negative numbers (SEC-10), and refuses signals with unknown keys (`isKnownPlatformSignals`, CR-01: a page could otherwise fill the 10 MB storage through cards, recent syncs and the queue). Stored URLs that become links are revalidated on read: the Watching cache (SEC-04), the recommendations batch (`isRecoBatch`: `siteUrl` on anilist.co, platforms on their host, a bad batch is recomputed, SEC-02), history links in `buildPlatforms` and the stored AniList profile (`isAniListViewer`: anilist.co only, SEC-03).
- **Tracker writes** (`refactor/entry-commands`, audit 1-I6 / 6-P3): every write to an entry goes through `background/entry-commands.ts` › `runGuarded` (session check → entry lock → fresh read → pure decision → session re-check → write), used by live sync (`sync-service.ts` › `decideEntryWrite`), the history import (`importOnService`) and, through `runOnServices(targets, EntryCommand, epochs)`, the list actions (`controls.ts`: +1 / −1, status, add; `engagement.ts`: rating, rewatch, comment, removal), each with the sessions read before any request (or the « À noter » card's); a session closed during the action answers `sync.sessionClosed`, or « Session expirée » (`TOKEN_INVALID`) when the read itself had the token refused (the anonymous replay of the read closes the session). One service → id resolution, `entryTargetId` (AniList = catalog or screen id; MAL = catalog `idMal`, else the screen's; `engagement` reads the catalog only when MAL is connected and the screen has no `idMal`). Not yet: `compare.ts` › `processItem` (no epoch on the job, relies on the job being deleted at sign-out) and L2 (token read at request time, not bound to the epoch). `addRecentSync` refuses a sync none of whose sessions is still open (L3). Marking a rewatch « Terminé » never queues a rating (`shouldQueueRating` › `wasRepeating`, like `shouldPromptRating`). Tracker codecs (`refactor/tracker-codecs`, 6-P2): service → entry id is `shared/tracker.types.ts` › `entryIdOn` everywhere (compare, import plan, entry links, `resolveId`, `entryTargetId`); scores go through `shared/score.ts` › `ScoreCodec` (`MAL_SCORES`, `aniListScores(format)`, `scoreCodec(service, format)`: `encode` / `decode` / `on10`; `toMalScore` absorbed `malScoreFrom`), with a contract test run on every codec plus the AniList ↔ MAL parity (`score.test.ts`); `TrackerService.fullList()` gives the import its `{ id, status, progress }` list; one MAL status table (`LIST_STATUS_TO_MAL`, read both ways) and one `malStatusFields` writing `status` + `is_rewatching` together. Not moved: `page-media.ts` › `toScore10` still branches on the service (another refactor owns that file). « Retirer de la liste » (no service in error) also drops the queued syncs whose season mapping points to the series and the simple « À vérifier » cards suggesting it, created before the removal (`dropQueuedSeries`, decision 18); corrections are kept.
- **`https://` patterns only** (SEC-02, `fix/https-patterns`, 2026-10-16): every host pattern (`host_permissions`, `optional_host_permissions`, `content_scripts` matches, registered scripts, `web_accessible_resources`) is `https://`, never `*://` (a `*://` pattern also ran the scripts, the Crunchyroll MAIN bridge included, on plain http pages a network attacker could serve); enforced on the sources (`scripts/store-permissions.test.ts`, `registry.test.ts`) and on the built packages (`build-checks.ts` › `checkHttpsPatterns`). Access granted by ≤ 2.3.1 under `*://`: Chrome narrows the stored active permissions to the new manifest on load (`GetBoundedExtensionDesiredPermissions`, intersection `kPatternsContainedByBoth`: `*://*.netflix.com/*` → `https://*.netflix.com/*`, checked in a real Chromium by `scripts/ext-e2e/access-migration.ext.ts`); Firefox keeps the granted string as is (`ExtensionPermissions`, no revocation outside enterprise policies today), `contains(https://…)` stays true (`allowedOrigins.subsumes`) but `remove(https://…)` does not remove it (exact string match), so `removePlatformAccess` removes `legacyAccessMatches` (`platforms/registry.ts`) second when access remains, and `touchesPlatform` accepts the legacy origin in `onRemoved`. Never one `remove` call with both patterns: Chrome rejects the whole call for a pattern not in the manifest. Open risk: Firefox bug 2022704 (extend the policy-only revocation of granted origins no longer subsumed by the manifest to every add-on) would revoke the legacy `*://` grants (Netflix / Disney+ / Prime access, and Crunchyroll / ADN host access) at the next update; the toggle and the host-access banner then show it, one click restores it.
- **CSP of the extension pages and the service worker** (SEC-12, `chore/csp`, 2026-10-16): `default-src 'self'; script-src 'self'; object-src 'self'; img-src 'self' data: <IMAGE_HOSTS>; connect-src 'self' <API origins of host_permissions>; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, kept in sync by `background/network-csp.test.ts` (exact directives, `img-src` = `IMAGE_HOSTS`, `connect-src` = `'self'` (lazy locale catalogs, `fetch(new URL(url, import.meta.url))`) + the non-streaming `host_permissions`, every fetch constant of the AniList / MAL clients inside it) and by `verify-build` › `checkContentSecurityPolicy` on both packages. A new API host = `host_permissions` + `connect-src` + its URL constant in the test. No `style-src`: styles fall back to `'self'` (bundled CSS, woff2 fonts), so an inline style attribute is refused: set styles through the CSSOM (`el.style.x = …`; `h()` maps `attrs.style` to `style.cssText`), never `setAttribute('style', …)` (static test). Content scripts are not concerned (the page's CSP applies to them). `test:ext` records every CSP violation of the watched pages and of the service worker (CDP `Log.entryAdded`, source `security`; `h.cspViolations`, asserted empty by `expectCleanRun`, page tour in `csp.ext.ts`). `npm run dev` (Vite serve, HMR over `ws://localhost`) is not covered by `connect-src` and was not checked.
- **Images and messages**: every displayed image goes through `toImageSrc` / `toSafeImageUrl` (`shared/url.ts`, `IMAGE_HOSTS` hosts), which must stay identical to `img-src` in `content_security_policy.extension_pages` (test). Each message type declares its senders in `MESSAGE_ORIGINS` (`background/message-guards.ts`); a new message sent by a content script must be `content` or `both` there (static test).
