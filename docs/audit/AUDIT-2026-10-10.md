## SYNC — Sync

### SYNC-01

**A prequel or sequel that is ANOTHER series on the platform joins the seasons and receives the progress (confidence high, match cached)**

- **Severity:** 🟠 high · **Status:** confirmed
- **File:** `src/background/sync/resolver.ts:108`

**Problem.** collectCandidates propagates the "relation" link to every SEQUEL or PREQUEL entry (TV, TV_SHORT or ONA format) of a linked entry. This holds even when that entry has its own Crunchyroll link to ANOTHER seriesId: linkOf then returns null, and line 115 marks it as 'relation'. seasonPool (matching.ts:245) keeps it as a season of the series, sorted first by date. resolveTarget then counts seasons from index 0: step 4 (matching.ts:571-577), step 2 and step 3b with walkSeasons(pool, 0, …). Since linked.length > 0, level() returns 'high' and resolveEpisode saves the match (resolver.ts:234-237).

**Scenario.** Crunchyroll, "Naruto Shippuden" S1 E5. AniList: Shippuden (1735, linked by slug) has Naruto (20, TV, 220 episodes) as PREQUEL, which is fetched and marked 'relation'. Result: entry 20 (Naruto), progress 5, confidence high. Naruto is then added or updated at episode 5 on AniList and MAL, and the s2→Naruto match is cached for the whole season. S2 E3, displayed as E35, likewise gives Naruto, progress 35 (absolute numbering). Result confirmed by running resolveTarget on these candidates. The same pattern is expected for Bleach TYBW (prequel: Bleach) and any sequel published as a separate series.

**Proposed fix.** Distinguish "linked to another series on the platform" from "not linked": add a LinkKind 'other', returned when the URL points to the same platform with another seriesId or slug. Never propagate a link to or through an 'other' entry, and exclude it from seasonPool. Failing that, only count a 'relation' entry if it has no link to the platform. Add a Naruto/Shippuden test in matching.test.ts.

### SYNC-02

**AniList ↔ MAL alignment writes a stale snapshot without re-reading and can roll back progress and status**

- **Severity:** 🟡 medium · **Status:** confirmed
- **File:** `src/background/compare.ts:228`

**Problem.** processItem builds the write from the stored comparison (compare:last), through findDiff and planApply. It then calls tracker.saveEntry without re-reading the current state of either service. The comparison stays stored indefinitely (analyzedAt is only used for display) and is not invalidated by live sync, the import or the controls. planApply writes the source's status, progress and repeat as they were at analysis time.

**Scenario.** Monday, analysis: Frieren AniList 5, MAL 3 (difference listed). Tuesday to Thursday, live sync brings both services to 8. Thursday, the user clicks "Match MAL to AniList" on the difference still displayed: saveEntry writes progress=5 and status=CURRENT to MAL, which goes back from 8 to 5. With MAL as the source, AniList goes back to 3. A series completed in the meantime can also return to CURRENT.

**Proposed fix.** Before writing, re-read both entries with getEntry (source and target), like applyItem in cr-import. If either one differs from the snapshot (progress, status or repeat), skip the item with a message "difference changed since the analysis, run the analysis again". Otherwise, at a minimum, refuse a progress write lower than the target's current one, and invalidate compare:last after each successful sync of the same entry.

### SYNC-03

**Manual review: a transient MAL (or AniList) failure is lost (card deleted, nothing queued)**

- **Severity:** 🟡 medium · **Status:** confirmed
- **File:** `src/background/sync/sync-service.ts:184`

**Problem.** resolveReview calls writeToServices without going through recordSyncOutcome (background.ts:127-131): a service with a transient error is never added to the retry queue. Yet writeToServices deletes the card as soon as one service is not in error. The partial failure is therefore neither retried nor offered again.

**Scenario.** "To check" card for "Kaiju No. 8 S2 E12" (finale). The user confirms: AniList is updated and moves to COMPLETED, MAL returns 504 or is offline. The card disappears and the queue is empty. Since the match is cached, no later episode will catch MAL up: the MAL entry stays at 11, never completed, with no trace at all in Activity.

**Proposed fix.** In the RESOLVE_REVIEW handler, pass the result through recordSyncOutcome(review.episode, null, outcome), exposing the episode from resolveReview. Another option: only delete the card if no service has a transient error.

### SYNC-04

**Rating prompt after sync even if the series is already rated, at the end of a rewatch, or when only the split MAL entry completes**

- **Severity:** 🟡 medium · **Status:** confirmed
- **File:** `src/background/sync/sync-service.ts:139`

**Problem.** buildPrompts triggers prompts.rate as soon as a service moves to COMPLETED. It does not check whether the entry already has a rating: current.entry.score is available in writeToService but is not passed up. setListStatus does perform this check (controls.ts:142, shouldQueueRating). The content script's rating bubble then calls rateMedia, which overwrites the rating on every service. The end of a rewatch (REPEATING → COMPLETED, rules.ts:50-51) therefore always triggers a rating request for a series that is already rated. Same thing if only the MAL entry, split shorter than AniList's, completes.

**Scenario.** Series rated 9/10 on AniList, rewatch in progress. At the last episode, sync moves it to COMPLETED (repeat+1) and the "Rate" bubble appears, even in full screen. Clicking 6 replaces the 9 on AniList and MAL. Another case: AniList has one 24-episode entry and MAL two 12-episode entries. At episode 12, MAL moves to COMPLETED and the requested rating is also written to the AniList entry, still at 12/24.

**Proposed fix.** Add `scored: current.entry?.score !== undefined` to ServiceWrite and reuse shouldQueueRating. Only offer the rating if no service has a rating, if the entry was not REPEATING, and if the AniList entry (catalog) is completed.

### SYNC-05

**Cached match with episodes:null never invalidated: sync stuck on "beyond the entry"**

- **Severity:** 🟡 medium · **Status:** confirmed
- **File:** `src/background/sync/matching.ts:175`

**Problem.** applyMapping only rejects a cached match if the progress exceeds mapping.episodes. That total is frozen at caching time: null for an airing entry with an unknown episode count. Once AniList publishes the total and creates the sequel as a separate entry (Part 2), the match still applies. resolveEpisode then returns 'Correspondance en cache' (high) without resolving again. writeToService then refuses the write (progress > current.episodes): a silent "skipped" at every episode, with no fallback to resolution.

**Scenario.** CR season S2 cached while "X Season 2" was airing (AniList episodes=null). AniList then sets 12 episodes and creates "X Season 2 Part 2", which Crunchyroll keeps in S2 (episodes 13 to 24). Each episode 13 to 24 resolves from the cache to Part 1, progress 13 to 24, then is skipped with "beyond the entry" on AniList and MAL. Part 2 is never updated and no review card appears.

**Proposed fix.** In syncEpisode, when the target comes from the cache and the catalog (getCatalogMedia) reports a total lower than the progress, delete the match and run resolveEpisode again. More simply: revalidate mapping.episodes against catalog.episodes and update it if it was null.

### SYNC-06

**Permanent errors (MAL 404, deleted AniList entry) classified as "transient": 6 useless retries, then repeated failure without invalidating the cache**

- **Severity:** ⚪ low · **Status:** confirmed
- **File:** `src/background/sync/queue-policy.ts:19`

**Problem.** RETRYABLE_CODES contains API_ERROR, the code of every HTTP error: malRequest returns API_ERROR for a 404 (mal.ts:132), and the AniList client does so for a 4xx GraphQL error (client.ts:89-91). The queue therefore retries, for 24 h, writes that cannot succeed. The job runner already makes the distinction: transientKind only keeps 500 to 504. For a merged or deleted AniList entry, the cached match is never forgotten and every new episode fails the same way.

**Scenario.** Wrong idMal on AniList, MAL returns 404 "anime not found". The 'synced' result with MAL in API_ERROR is classified as "retry", and the item stays pending for 6 attempts (1 min to 6 h) before moving to "failed". Another case: the cached entry was merged on AniList. getCatalogMedia fails with a 404, the overall result is a retryable error, the episode is queued, and every following episode of the season does the same.

**Proposed fix.** Pass httpStatus in ServiceOutcome and SyncOutcome, and only retry API_ERROR for a status ≥ 500 or a timeout, like transientKind. On a 404 for the cached entry, delete the match (deleteMediaMapping) to force a new resolution.

- **File:** `src/shared/storage.ts:140`

### DATA-03

### BAK-01

**Imported correction card: writing downward is allowed, progress can go back and a completed series can return to watching**

- **Severity:** ⚪ low · **Status:** confirmed
- **File:** `src/shared/sync.types.ts:27`

## CRI — Crunchyroll history import

### CRI-01

**A single transient error on one page or one season lookup loses the whole read**

- **Severity:** 🟡 medium · **Status:** confirmed
- **File:** `src/content/lib/crunchyroll-history.ts:98`

**Problem.** paced turns any fetch exception into CrHistoryError('network'). get throws 'blocked' on the first 403/429 and 'unavailable' on any non-OK status, including a transient 5xx. No retry or wait is planned. During the season lookup phase, only the 'unavailable' error is tolerated: 'network' or 'blocked' on a single season aborts the whole read. Yet this read can take a long time: up to 100 pages, then up to 2000 lookups spaced 300 ms apart, i.e. more than 10 minutes.

**Scenario.** Large history: 80 pages read, then 900 season lookups. A one-off 429 or a one-second Wi-Fi drop on the 901st lookup → `throw error` → "blocked" or "network" message, nothing is sent, and the user has to start over from the beginning.

**Proposed fix.** Add a few retries with increasing backoff in get for 'network', 429 (honoring Retry-After) and 5xx. During the season lookups, treat a persistent transient failure as an unknown position (null → "To check") instead of aborting the whole read.

### CRI-02

**Non-atomic read then write in applyItem: the "never go back" guarantee can be broken**

- **Severity:** ⚪ low · **Status:** confirmed
- **File:** `src/background/cr-import.ts:233`

**Problem.** applyItem re-reads the entry (tracker.getEntry), decides with decideImport, then waits for waitWriteSlot before tracker.saveProgress. waitWriteSlot waits for the write spacing and above all for aniListBudget.acquire('background'), which lets interactive traffic through first (popup, live sync). During that wait, a live sync can write a more advanced progress. The import then writes an absolute value decided on a stale state. There is no per-entry lock or version check between the read and the write.

**Scenario.** Applying an import of several hundred series runs in the background while the user watches series X on Crunchyroll. The import reads X at 5/12 and decides "11, CURRENT", then waits for the background budget, delayed by the interactive sync. Meanwhile, the live sync writes 12/12 COMPLETED. The import then writes 11 CURRENT: progress goes back and the Completed status is lost.

**Proposed fix.** Take the write slot (waitWriteSlot) BEFORE the fresh read, so the read and the write follow each other without waiting. Better: serialize the import and the live sync per entry (lock per mediaId), or re-read right after the write and fix any regression.

### CRI-03

**Account change while applying: no session generation check**

- **Severity:** ⚪ low · **Status:** confirmed
- **File:** `src/background/cr-import.ts:218`

**Problem.** The trackers are taken once at the start of applyItem. Each call (getEntry, saveProgress) then reads the current token from storage. Sign-out does clear the crImport:* keys (storage.ts L142, L186) and increments sessionEpoch, but the item in progress ignores it: neither getSessionEpoch nor saveCachedWatching(epoch) is used, unlike api/watching.ts L242-247. **Scenario.** During an AniList budget wait ("quota" pause, several tens of seconds) between getEntry and saveProgress, the user disconnects account A then connects account B. saveProgress goes out with B's token and a decision computed on A's entry (A at 5 → write 12): B's entry, at 20 or COMPLETED, is overwritten with 12 CURRENT. Another case: a finalize running at sign-out time writes crImport:plan back with the old account's list.

**Proposed fix.** Capture getSessionEpoch(service) at the start of applyItem and finalize. Check again right before saveProgress and before writing the plan, and drop the item or the job if the generation has changed (same pattern as saveCachedWatching).

### CRI-05

**Retrying an item: a successful write is reported as skipped or failed, and the match is not remembered**

### CRI-06

**Crunchyroll's private client ID and imprecise rotation diagnosis, incomplete Store justification**

- **Severity:** ⚪ low · **Status:** plausible
- **File:** `src/content/lib/crunchyroll-history.ts:15`

## ALRT — Airing alerts and schedule

**Progress and followed series read from a "Watching" cache that the alarm never refreshes**

### ALRT-02

**Lowering the alert delay: episodes released in the gap are never notified**

### UI-01

**"Now playing" panel stuck loading when the tab updates while the entry is being resolved**

- **Severity:** 🟠 high · **Status:** confirmed
- **File:** `src/sidepanel/components/now-playing.ts:323`

**Problem.** refresh(false), called by setTab on every update of the tracked tab, increments `run`. The pending resolve() then drops its response (`if (current !== run) return`). The page is identical, refresh exits, and the resolve response is discarded. The skeleton stays on screen indefinitely. **Proposed fix.** In refresh(), only exit early if the entry is stable, for example `if (!force && known && sameKey && settled()) return;`. ### UI-02

**The result of a panel action reloads the old page after a tab or episode change**

## SEC — Security and privacy

### SEC-01

**OAuth tokens (including the MAL refresh token) stored in plain text in chrome.storage.local, readable by content scripts**

- **Severity:** ⚪ low · **Status:** confirmed
- **File:** `src/shared/storage.ts:54`

**Problem.** CLAUDE.md requires never storing OAuth tokens in plain text. In the code, saveToken (l.54) and saveMalToken (l.169) write { accessToken, refreshToken, expiresAt } as-is to chrome.storage.local. Nothing is encrypted and setAccessLevel is never called. By default, storage.local is accessible to untrusted contexts, and content scripts already use it: getSettings() in src/content/lib/watch-session.ts:34 and src/content/lib/cr-history-port.ts:49, via src/shared/settings.ts:147. The MAL refresh token is long-lived and the AniList token lasts about a year. Both are therefore readable from the Crunchyroll, ADN and Netflix page processes. The service worker's EXTENSION_PAGE_ONLY filter does not protect against this path.

**Scenario.** A flaw in the renderer or code execution in the content script's isolated world on crunchyroll.com, animationdigitalnetwork.com or netflix.com: a call to chrome.storage.local.get(['anilistToken','malToken']) returns the tokens in plain text. The attacker can then modify or wipe the user's AniList/MAL lists for months (the MAL refresh renews indefinitely), and disconnecting on the SyncKai side revokes nothing.

**Proposed fix.** Encrypt the tokens before writing: AES-GCM with a non-extractable CryptoKey generated once and kept in the extension origin's IndexedDB (inaccessible to content scripts). Decryption happens only in the service worker (getValidToken, getMalToken). Another option: move the tokens out of storage.local. setAccessLevel only applies to storage.session and does not survive a browser restart. If the current storage is kept, fix CLAUDE.md so it does not promise what is not done.

**Problem.** For each analyzed season, `analyzeSeason` calls `readInput()`, which re-reads all of `cr-import:input` (up to MAX_HISTORY_SEASONS = 2000 seasons) and fully revalidates it (`isCrImportInput` → `isCrHistoryResult`). It then calls `writeResolution()`, which re-reads the whole `resolutions` object (with the review candidates), revalidates it (`readResolutions`) and rewrites it with one more entry. When applying, `applyItem` re-reads the full plan (`readPlan` + `isCrImportPlan` on all items), then `updatePlan` re-reads and rewrites all of it for a single `result`. `rememberMappings` calls `getMediaMapping`, which re-reads and revalidates all matches, then `saveMediaMapping`, which re-reads and rewrites all of them. The runner adds 3 to 4 job writes per item (`item-start`, result, `touch` every 10 s). The volume read and written therefore grows in O(n²). Each write also triggers `storage.onChanged` in the import page, which calls `setPlan` then `draw()` → `app.replaceChildren(render())` (import-cr.ts:87-89, 117-135).

**Scenario.** A long-time subscriber starts importing a history of 1500 seasons. The analysis re-reads an `input` of about 500 KB about 1500 times (about 750 MB of deserialization and validation) and rewrites `resolutions` 1500 times at a growing size (hundreds of MB written in total). The service worker stays CPU-bound for the whole analysis, the import page redraws on every write and, if several Crunchyroll tabs are open, each write is also broadcast to them (see the storage.onChanged item). The import becomes noticeably slower than the AniList request budget alone would require.

**Proposed fix.** In the loop, keep in memory the input and the plan read once at startup (and only re-read them after a resume or a service worker wake-up). Store resolutions and results under per-item keys (`cr-import:res:{index}`, `cr-import:result:{id}`) instead of a single rewritten object, or group them in batches (e.g. every 20 seasons or 5 s). Only publish the aggregate in the plan. For `mediaMappings`, read the object once per batch and write the new matches in one go.

### PERF-03

**Each content script listens to storage.onChanged: every large chrome.storage.local write is serialized to all streaming tabs**

- **Severity:** ⚪ low · **Status:** plausible
- **File:** `src/i18n/index.ts:98`

**Every popup or panel opening refetches the AniList profile, the MAL profile and the "Watching" list with no freshness threshold**

### PERF-05

**storage.session caches `pageMedia:{tabId}` and `panelMedia:v2:{id}` never purged (closed tabs, expired entries)**

- **File:** `src/shared/page-media-cache.ts:93`

**Problem.** preserveFocus finds the active element by its data-focus after the new render. Two cases fall outside this mechanism. ## ARCH — Architecture recommendations

*Recommendations from the architects, filtered by a second architect (only the ones kept, with adjusted priority), plus the additional issues the second architect raised.*

### ARCH-01

**Stop rewriting host sites' `<html lang>` from the content script** — priority medium, effort S

**Problem.** The i18n module has a DOM side effect meant for the extension's pages, but it also runs in content scripts. `initI18n()` runs `document.documentElement.lang = current` (src/i18n/index.ts:92) and `setLocale()` does the same (line 46). Yet `startContent()` calls `initI18n()` on every Crunchyroll, ADN and Netflix page (src/content/start.ts:25). The site's language is therefore replaced by the SyncKai UI language (fr/en/de). The history import then reads this rewritten value as the Crunchyroll language: `pageLocale(document.documentElement.lang)` (src/content/lib/cr-history-port.ts:54, crunchyroll-history.ts:431). Example: a Spanish-speaking Crunchyroll user with SyncKai in English gets "en-US" titles instead of "es-419".

**Recommendation.** Restrict writing `lang` to the extension's pages: an `initI18n({ setDocumentLang: false })` option passed by start.ts, or a `location.origin === new URL(chrome.runtime.getURL('')).origin` condition. On the import side, store the page language before any initialization (or read it again from another source), then pass it to `readCrunchyrollHistory`. Add a test: after `initI18n()` in a non-extension context, `document.documentElement.lang` stays unchanged.

**Risk if ignored.** Imported titles in the wrong language, hence a poorer AniList match and more "To check" cards. Visible effects on host sites: Chrome's translation offer triggered wrongly, screen readers speaking in the wrong language. It is also a modification of a third-party page that a store review could flag.

**Files.** `src/i18n/index.ts`, `src/content/start.ts`, `src/content/lib/cr-history-port.ts`, `src/content/lib/crunchyroll-history.ts`

**Second architect's opinion.** Confirmed. src/i18n/index.ts:46 and :92 write `document.documentElement.lang`. src/content/start.ts:25 calls `initI18n()` on every page, and src/content/lib/cr-history-port.ts:54 then reads this value back via `pageLocale`. This module is wired in content.ts:6 on the same page. The impact is narrower than the report says: it only affects users whose Crunchyroll language differs from SyncKai's, or whose region is lost (the rewritten value "fr" gives "fr-FR" via the defaults in crunchyroll-history.ts:437, so es-ES becomes es-419). The fix is cheap and should be done: an `initI18n({ setDocumentLang: false })` parameter on the content side. Priority medium rather than high, since nothing breaks across the board.

### ARCH-02

**Create a platform registry and generalize the "optional platform" mechanism before Prime Video / Disney+** — priority medium, effort M

**Problem.** Adding a platform currently means touching more than 10 unrelated places. Union and Record: shared/episode.types.ts:3 and PLATFORMS. Link matching: `matchPlatformLink` (background/sync/matching.ts:151-167) and `LINK_REQUIRED_PLATFORMS` (line 590). Two `switch` statements in shared/platform-links.ts (lines 78 and 127). Labels: `PLATFORM_LABELS` stored in popup/components/ui.ts:15. Elsewhere: ui/brand-icons.ts, shared/settings.ts. Above all, the "optional access" mechanism is hardcoded for Netflix: NETFLIX_MATCHES (shared/target-pages.ts), shared/netflix-access.ts, background/netflix-access.ts and netflix-scripts.ts, about thirty mentions of Netflix in ui/settings/page-sync.ts and the literal 'netflix' in ui/settings/summary.ts:42. Finally, the secure transport of the MAIN bridge (handshake, MessageChannel, trusted port) is mixed with the Netflix-specific reduction in content/netflix/bridge-protocol.ts. Prime Video and Disney+ will also be optional general-purpose catalogs, probably in the MAIN world: everything would be copy-pasted.

**Recommendation.** Create `shared/platforms.ts`: one descriptor per platform (id, label, host patterns, `optional`, `linkRequired`, building series and search URLs, AniList link test), consumed by matching, platform-links, the UI and the settings. Turn netflix-access/netflix-scripts into an `optional-platforms.ts` parameterized by descriptor, with a generic toggle in the settings. Extract the bridge transport into `content/lib/main-bridge.ts`, with a request and response codec specific to each platform. Do this work on a `chore/platform-registry` branch before the Prime Video exploration.

**Risk if ignored.** Each new platform copies the sensitive code of the MAIN bridge and of the dynamic registration, with a risk of security divergence. Silent omissions are likely (label, search link, anime filter). The settings become a series of ad hoc blocks.

**Files.** `src/shared/episode.types.ts`, `src/background/sync/matching.ts`, `src/shared/platform-links.ts`, `src/popup/components/ui.ts`, `src/shared/target-pages.ts`, `src/shared/netflix-access.ts`, `src/background/netflix-access.ts`, `src/background/netflix-scripts.ts`, `src/ui/settings/page-sync.ts`, `src/ui/settings/summary.ts`, `src/content/netflix/bridge-protocol.ts`

**Second architect's opinion.** The scattering is real: PLATFORM_LABELS is stored in popup/components/ui.ts, plus matching.ts, platform-links.ts and the netflix-* files. However, generalizing the optional mechanism and the MAIN bridge transport now means speculating on two platforms that have not been explored yet (CLAUDE.md plans a technical exploration first). It is better to limit the work to the `shared/platforms.ts` descriptor (label, hosts, linkRequired, URLs), done when adding the 4th platform. Extracting `main-bridge.ts` and `optional-platforms.ts` should wait until Prime Video confirms it needs them (rule of three). Actual effort: S to M for the registry alone.

### ARCH-03

**Slim down the content script bundle (message guards and i18n catalogs)** — priority low, effort M

**Problem.** messages.ts imports the guards from compare.ts, agenda.ts and cr-import.ts as values (lines 1, 15, 17-26). The path start.ts → messages.ts → compare.ts → storage.ts therefore pulls storage, job, the queue, the schedule, watching and i18n into the content script. i18n in turn pulls the 3 full catalogs (841 keys each, about 150 KB). It contains the compare, agenda and crImport strings. The Netflix IIFE, which cannot be split, weighs 197,253 bytes. The service worker is the only user of `isRuntimeMessage`.

**Risk if ignored.** About 255 KB parsed on every full load of a Crunchyroll or ADN page, contradicting the "no heavy code in content scripts" rule. The weight grows with every UI feature, since each new i18n key and each new message guard ends up there.

**Files.** `src/shared/messages.ts`, `src/content/start.ts`, `src/i18n/index.ts`, `src/shared/compare.ts`, `src/content/netflix/content-netflix.iife.ts`, `vite.config.ts`

**Second architect's opinion.** The figures are consistent: dist/assets/logger-*.js weighs 166,912 bytes, and messages.ts imports compare.ts as a value, which imports storage and i18n (compare.ts:4 and :9). Point 1, however, has little effect. The content code imports i18n directly (watch-session.ts:1, toast.ts:1, sync-toast.ts:1, engagement-prompt.ts:1), so the 3 catalogs stay bundled even after splitting messages.ts. The only real gain would come from a reduced or per-language catalog, which complicates the build. ### ARCH-07

### ARCH-08
