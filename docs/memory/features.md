# Features

Keyboard shortcuts, account menu stats, the popup Stats screen and its activity history, airing alerts, the Schedule's « Announced » view. Part of the project memory (`CLAUDE.md` › Project memory).

- **Shortcuts `Alt+Shift+K` (complete episode) and `Alt+Shift+1` (side panel, `Alt+Shift+&` on AZERTY)**, identical on Chrome, Brave and Firefox (decision of 2026-10-11, `SUGGESTED_KEYS` in `src/build/manifest-target.ts`; before: `Alt+Shift+S` / `Alt+Shift+P`). Chrome auto-assigns a suggested key (install or update, `command_service.cc` › `CanAutoAssign`) only if the user didn't change that command's key and the key is not a Chrome accelerator nor taken by another extension; otherwise it stays unset and must be set in `chrome://extensions/shortcuts` (old `Alt+Shift+P` = Chrome's *New tab group*, `accelerator_table.cc`, hence never assigned). Firefox applies the manifest key on every load unless the user changed it (`ExtensionShortcuts.loadCommands`). At most 4 suggested keys (Chrome limit, checked by `scripts/build-checks.ts`). Command names in `protocol/commands.ts`.
  - Chrome (toggle, any tab): `open-side-panel` is handled in `background/side-panel.ts` › `togglePanelFromCommand`, fully synchronous (`sidePanel.open()` needs the user gesture, lost at the first `await`): global `setOptions({ path, enabled: true })` not awaited + `open({ windowId })` (`browser/side-panel.ts` › `openSidePanel`). Closing: the service worker keeps no state (lost when it sleeps). Once `open()` settles (a no-op on an open panel) or is refused, it broadcasts `SIDE_PANEL_TOGGLE` (`protocol/panel-toggle.ts`: `windowId`, `commandAt`); the panel page of that window (`windows.getCurrent()`) that loaded before `commandAt` closes itself (`sidepanel/toggle.ts`: `sidePanel.close({ windowId })` on Chrome 141+, else `window.close()`). Closing always follows opening, so the panel is never reopened right after closing.
  - Firefox: `manifest-target.ts` renames it to the native `_execute_sidebar_action` (toggles the sidebar on any tab, never reaches the background script).
  - Choice of keys: on Windows/Linux, Firefox treats Alt+Shift+<letter> like Alt+<letter> and opens the menu with that access key (`Alt+Shift+S` opened *History*, `Alt+Shift+P` *Profiles*, seen by the owner). Never suggest a letter that is a menu access key in the EN/FR/DE menu bar (`FIREFOX_MENU_ACCESS_KEYS`: A B C D E F H L M N O P S T V X, from mozilla-l10n `menubar.ftl`, *Profiles* included); `checkCommands` rejects it on the Firefox build, digits are accepted. K and 1: no Chrome accelerator (`accelerator_table.cc`: Alt+digit selects a tab on Linux, not Alt+Shift+digit), no Firefox default Alt+Shift shortcut (`browser-sets.inc.xhtml`). Keys next to K / 1 were rejected by the owner (accidental "watched").
  - Digits on AZERTY: Firefox turns `Alt+Shift+1` into `<key keycode="VK_1" event="keydown">` (`ShortcutUtils.getKeyAttribute`: only A-Z use `key`), matched on the DOM `keyCode` (`KeyEventHandler::KeyEventMatched`), which Gecko sets to 49 for the &/1 key (Windows native VK_1; elsewhere the Shift+key character "1"). Chrome matches the Windows virtual key (VK_1). So the physical key works on AZERTY; the UI shows `commands.getAll()` (« Alt+Maj+1 ») plus, in French only, « (touche &) » (`azertyKeyHint`, digits common to French and Belgian AZERTY).
  - UI: *Settings › Display › Shortcuts* (`ui/settings/page-shortcuts.tsx`) is the only place that shows the keys (`commands.getAll()`, reread when the view regains focus) and opens the browser's shortcuts page (`ui/shortcut-settings.ts`); the *Display* row that opens it has a short description, never the keys (owner's decision on the mockups).
- **Account menu stats and weekly counter** (`feature/ui-account-menu`, 2026-10-17): the profile stats ride on the profile request (AniList `Viewer.statistics.anime { count episodesWatched minutesWatched }`, MAL `/users/@me?fields=picture,anime_statistics`), so they share its cache (`anilistViewer.stats` / `malViewer.stats`, `null` = unreadable, absent = cached before) and its epoch-checked write; the menu re-reads the profile once on open when it is older than 1 h (`ACCOUNT_STATS_TTL_MS`). Anime count = AniList `count`, which EXCLUDES « Planning » (measured on a public profile: statuses sum 325, count 258 = 325 − 67 planning), so MAL uses `num_items − num_items_plan_to_watch` (`shared/account-stats.ts`). « Synchro cette semaine » = `accountMenu:weeklySyncs` (`{ [service]: { weekStart, count, epoch } }`, Monday-based local week, scope `user`, the closed session's part dropped by `purgeClosedSessions`), +1 per service whose outcome is `updated` in `writeToServices` (live sync, queue retries, confirmed « À vérifier » cards), never for a correction (the episode was already counted), the history import, list alignment or the +1 / −1 / status actions; written under the storage lock for sessions still open (`recordWeeklySyncs`).
- **Stats activity history** (`feature/rail-activity`, 2026-11-11, call 1 of the rail sections spec): `stats:activityHistory` = `{ [service]: { accountId, days: { 'YYYY-MM-DD': [episodes, minutes] } } }` (`shared/activity-history.ts`), local days, the 400 days ending today (pruned on write; future days kept but outside summaries), written next to `countWeeklySyncs` with the same exclusions (`countActivity` → `recordActivity`: sessions still open, account id from the cached profile, skipped without one; minutes = the catalog's AniList `duration`, 0 when unknown; a failure never fails a sync). Scope `user` with `keepOnExpiry`: a token refused or unreadable on the last session keeps it (`afterSessionEnd('expired')` → `keysClearedOnLastSession('expired')`), the last voluntary sign-out drops it; not touched by `purgeClosedSessions` (keyed by account, not epoch). A saved profile of another account drops that service's part (`dropOtherAccountActivity` in `getViewer` / `getMalViewer`); a summary for another account (or none) is empty. In the Backup (9th key, merge = max per day for the same account, the existing part wins against another account; no session binding; on import: pruned to 400 days, another account's part dropped against the cached profile, `importableActivity` in `browser/storage/backup-store.ts`, 19ea7ca; a file without the section, made before 2.5.0, leaves it untouched, see Backup below).
- **Popup Stats screen** (`feature/rail-sections`, 2026-11-11, spec `2026-11-11-popup-rail-sections-design.md`): two sources, no new request. (1) The profile statistics (`shared/profile-stats.ts`) ride on the same `Viewer` / `anime_statistics` request and cache as the account menu (`profile`, `null` = unreadable, absent = cached before 2.5.0 → one refresh); re-read on opening once per service when older than `ACCOUNT_STATS_TTL_MS` (1 h). AniList: statuses, formats, `genres(limit: 6)`, `scores` in the user's `scoreFormat` (POINT_10_DECIMAL comes on a 100 scale: 65 → 6.5), `studios(limit: 5)`, `releaseYears` stored as decades; MAL: statuses, rewatches, mean score only, the other blocks hidden (MAL rule: nothing beyond `anime_statistics`). (2) The activity history above. Service switch only with both accounts, default `activeService()`, remembered with the « Pour toi » filter in `popupPrefs:sections` (`popup/controllers/section-prefs.ts`, merge-written: `popupPrefs` is rewritten whole on each sort change); the period is not remembered. Described in `PRIVACY.md` and the CWS `storage` block; `scripts/store-permissions.test.ts` (SEC-01) requires « Stats activity history » in the English policy.
- **Airing alerts follow the Schedule** (decision 17 = yes, 6-D13, `chore/audit-leftovers`): a notification fires at `alertAt` (`background/airing-policy.ts`) = `estimateRelease` of the Schedule (`shared/agenda.ts`: the series delay, else the delay of the platform of its « Open » link chosen by `mergeWatchingSeries` with the effective preferred player; the Japanese broadcast when neither is known) + the alert delay `airingDelayHours` (0 by default, kept as an extra margin). The cursor `airingCoveredUntil` stays in broadcast time: `alertWindow` reads broadcasts from it back to the largest delay of the followed series, up to the smallest (a negative delay reads upcoming broadcasts); `dueAlerts` keeps the due ones (alert time in (`notBefore`, now): 2 h on the first run, 24 h after) and holds the cursor at the broadcast of the earliest not-yet-due alert, so lowering a delay never skips an episode (ALRT-02). The texts `settings.airing.help`, `settings.offsets.help` and `airing.notification.message` still describe the Japanese broadcast time (owner's call to reword them in the 21 languages).
- **Sequel alerts wake the worker once a day** (PERF-04, `bugfix/sequel-alarm`, owner's decision 8 (a) of 2026-11-13): the daily pass has its own alarm `synckai:sequels` (`browser/airing-alarm.ts`), rescheduled after each pass; the hourly alarm exists only while release alerts are on and no longer runs the sequel pass. `checkSequels` keeps its not-due, 6 h failure backoff and force cooldown guards (an early alarm answers « not due » and reschedules).
- **Schedule › « Announced » is a calendar** (`feature/announced-calendar`, owner's decision of 2026-11-11): it groups by anime season (`shared/sequels.ts` › `groupSequelsByPeriod`, generic over the dated fields) the unlisted announced sequels (records, « + Plan to watch » and ×) and the series of the user's lists planned (not yet released or airing) or being watched and not yet released, formats TV / TV_SHORT / ONA / MOVIE (`listedQualifies`), shown by `SequelRow` with `listStatus` (« In your list · {status} », `sequel.listedAs`; no button, no ×, no « New »); an id in both shows the list row only. Gated by « Sequel alerts » like the records (`ui/sequels-store.ts` › `listed`). The popup Activity section and the rail dot stay records-only.
  - storage: `sequels:state` › `listed?: ListedEntry[]` (no source fields + `listStatus`, ≤ 200, by date), never checked by `isSequelStore` (a malformed `listed` must not reset `known` and renotify everything): always read through `listedEntries`. Replaced by each daily pass (`mergeSequelPass(…, listed)`), from the AniList full list (`AniListListEntry.release`, parsed by `parseRelease`; no extra request) or, MAL only, one public AniList `idMal_in` + `status_in` query per 50 PLANNING / CURRENT MAL entries (`fetch.ts` › `listedByMal`).
  - « + Plan to watch » that ends (popup, Schedule, notification button, watch order) sends `'listed'` (`listSequels`: record removed, `known` kept, snapshot into `listed` as PLANNING), so the row turns into the list row in place. `CHECK_SHOWN_SEQUELS` also covers `listed`: a record found PLANNING (or CURRENT not yet released) moves to `listed`, any other status removes it; a listed entry no longer in a list or with another status is dropped (`writeSequels`, locked and epoch-checked).
  - a known id without record that is a candidate again (removed from the list) is recreated `'seen'` with `firstSeenAt: 0` and never notified; `capRecords` ranks those below the dismissed ones, so an id pruned by the 200 cap stays pruned and never evicts a record; ties on `firstSeenAt` keep the lower ids, as displayed (`newestFirst`). Dismissed records keep their state.
  - the same holds for a source paused, dropped or excluded then resumed (SEQ-02, `sequels.test.ts`): its sequel comes back `'seen'`, never notified.
  - grouped notification « N suites annoncées » (click or its button, XB-02, owner's decision of 2026-11-13): `actions.ts` › `focusLastWindow` (`windows.getLastFocused({ windowTypes: ['normal'] })` then `windows.update(id, { focused: true })`), then `openPopupOn('activity', id)` (`action.openPopup({ windowId })`): Chrome and Firefox 149+ refuse `openPopup` for an inactive window. Fallback when it is refused (always on Firefox < 149: no user gesture from `notifications.onClicked`): the first visible sequel's AniList entry, in that window. The notification is cleared after the opening only.
  - a failed « + Plan to watch » (`SequelRow`, watch order `SequelActions`) carries `alertAttrs` (announced once by the live region), and the button's accessible name starts with the visible « Retry » (`sequelAddAria`: « Retry · Add {title} to Plan to watch », no new string; SEQ-03).
- **Dormant series** (« En sommeil » group of *My series*, 2.5.0; 2.5.1 fixes on `bugfix/dormant-follow-ups`, audit `docs/audit/2026-11-10`): rules in `shared/dormant.ts`, controller `popup/controllers/dormant.ts` (writes `SET_LIST_STATUS` with `onlyFrom`, one series at a time). A *Pause*, *Drop* or *Put all on hold* clicked while the shown list is the cache being revalidated waits for the fresh list and writes only the series still dormant in it; after a failed revalidation nothing is written (error banner, POP-03). Bulk runs share one pace (`popupTimeouts.dormantPaceMs` between two sends, a new bulk and an *Undo* running together included); *Undo* skips a series another run is writing and ignores *Keep* marks (they only stop a pause). *Keep* marks are keyed by the shown service's own id (`mal:<id>` on the MAL list, AniList id otherwise; a 2.5.0 AniList-keyed mark is still read on the MAL list, POP-08). The run stays in the popup (owner's decision 6 b of 2026-11-13; a service-worker job is 2.6): the button shows « n / N », and the undo set is kept in `chrome.storage.session` (`DORMANT_UNDO_KEY`, `browser/storage/dormant-undo.ts`: saved after each written series, 2 minutes, bound to the open sessions' epochs, cleared with its banner, on sign-out and at browser close), so reopening the popup shortly after closing it mid-run still offers *Undo* (POP-05). `setListStatus` drops the series from the worker's cached *Watching* list of each written service (PAUSED, DROPPED, COMPLETED) or marks that list stale (CURRENT), under the session epoch (POP-06).
- **Friends' average** (`shared/friends.ts` › `reduceFriends`): no average when AniList reports more followed users than the 50 read (`total > friends.length`): the page is sorted by status then score, its average would be biased (POP-07).
- **Backup: absent ≠ empty** (owner's decision 10 (a), `bugfix/backup-and-import`, 2026-11-13, STO-02 / IMP-01): `parseBackup` lists in `ParsedBackup.missing` the sections the file does not have (settings excepted, already `null`), and `applyBackup(…, missing)` never writes them, in « Fusionner » as in « Remplacer »: an older file (2.4.x without `recoDismissed` and `activityHistory`) keeps this device's dismissed suggestions and activity history. A section present but empty or unreadable is still replaced. « Contenu du fichier » shows `import.keptMissing` when `missing` is not empty. « Fusionner » keeps every correction card (`previous`, with its `deferred` episode) and fills the remaining `MAX_PENDING_REVIEWS` slots with the newest simple cards, current or imported (`capReviews`, the `savePendingReview` rule).
- **Remaining time** (« Mes séries » sort, Stats): `episodeMinutes` = AniList `duration` only (`background/anilist/watching.ts`): the AniList list query for AniList, the `CATALOG_BY_MAL_QUERY` node (same request as the enrichment, no extra one) for a MAL list; no node or no `duration` = length unknown, as before. MAL's `average_episode_duration` is not requested (TERMS-04, decision 15 (a), 2026-11-13).
